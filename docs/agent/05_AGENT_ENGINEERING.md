# Agent 总架构与工程边界

> 新 `agent/` 内部目标架构：职责、依赖、状态归属和生命周期的权威位置。逻辑模块不等于进程、crate 或必须创建的目录。
> 不替代根 `ARCHITECTURE.md` 的 C4 L1–2 产品地图，不修改公共协议，不描述已退役的旧线（`agent/runtime/`，考古走 Git 历史）。设计不是全部实施授权。

| 问题 | 权威位置 |

原理：**足够聪明的模型自主使用持续环境；薄 OS 骨干以稳定契约连接可替换组件，Core/ Foundation 提供最小可靠兜底，Composition 显式接线。** 内部实现可以变化，主体可观察行为、权限、来源、顺序、结果和生命周期契约不能随之破坏。

新增 App、信息来源或启动方式应主要由外层实现与组合完成，不重写基本循环。接口须有真实消费者和兑现机制，通知接口不等于保存了通知，历史接口不等于耐久历史。不以层数、模式、空接口或模块数量证明架构。

## 2. 拓扑与依赖

产品 C4 L1–2 边界保持不变：

```text
Human → Client → IM（公共事实唯一授权写者）
                  ↕ 公共协议 / Connector
          新 Agent 执行环境（私有事实）
                  ↕ Provider Adapter
               模型服务
```

本文范围内的逻辑数据流，不新增部署容器：

```text
App / 外部来源 → OS 接纳与必要保存
                  ├→ 可替换通知/状态组件 → 机械入口 → 主体按需查询
                  └→ 明确启动机会 → Core 唯一 Run / Turn 循环
                                       ↕ ModelPort → Provider Adapter
                                       ↕ ActionPort → OS 路由 → App
                                       ↕ 可靠性/提交契约 → Foundation / 存储适配
结束与确认前缀 → 历史组件 → 新 Run 主动查阅，形成新观察
Composition：构造、配置、持有并显式连接以上实现
```

代码依赖箭头表示使用右侧接口，不是调用方向：

```text
Core        → Foundation
OS 骨干     → Core / 必要 Foundation 契约
App         → OS 暴露的窄接入契约
OS 组件     → OS 定义的对应通知/状态/历史等窄契约
Adapter     → 所实现的内部接口 + 外部协议
Composition → 被选中的具体实现与配置
```

- Foundation 不依赖 Core；Core 不依赖 OS、具体 App、Provider。
- **App 互不依赖，只面向 OS 接口**：不导入/调用另一 App 实现、私有状态或其业务入口。需要协作时通过 OS 稳定能力契约，由 Composition 接线，不把一个 App 的展开或存活作为另一个 App 的隐式前提。
- OS 骨干不靠导入每个 App 业务类型并增添分支扩展；通知、状态、历史是可替换责任组件，不要求所有逻辑堆在单个 OS 对象里。
- 下层定义所需接口，外层实现。Core 调用 ModelPort 的外层实例，不是依赖具体 Adapter。
- App 的世界业务可通过外围 Adapter 访问外部系统；协议适配不构成 App 间依赖，不把供应商 SDK、网络格式或数据库驱动带入 Foundation/Core。
- 当前静态接线是否符合目标只在 README 判定，不把目标图当作已实现通用框架。不预建万能注册中心、事件总线或插件框架。

## 3. 模块职责

| 模块 | 拥有的责任 | 不拥有的责任 |
|---|---|---|
| Foundation | Fact/Ledger、Operation identity、Effect、Receipt、Unknown、恢复依据、隔离及必要时间/存储契约 | App 正文、任务判断、调度 |
| Core | Run、Turn、Trace、View 边界、模型验证、Action/Observation/Outcome、注入时机、唯一循环及恢复边界 | 来源业务、通知、唤醒、Provider wire、长期记忆 |
| OS 骨干 | 身份与权限接入、能力入口/路由、资源/生命周期组织、共同契约 | 自动规划、摘要、优先级、具体 App 业务对象 |
| 通知/状态/历史组件 | 按 OS 契约保存、组织与提供各自机械信息及授权查阅 | 改写 Core 循环或主体经历、替主体判断重要性 |
| Apps | 具体世界的数据、动作、局部验证、结果、变化来源与专属展示 | 改 Run、旁路授权、另起执行链、调用其他 App 内部 |
| Adapters | 内外协议准确翻译，Provider/Storage/Connector 实现 | 猜行动、静默丢内容、用外部概念定义主体 |
| Composition | 配置、授权参数、构造、持有与显式接线 | 第二循环、隐藏业务政策、万能 Host |

少一个 App 主要减少一种能力；Core/OS 共同行为错误影响所有能力。共同规则不能靠不断加 App 弥补，也不因手机比喻反复拆合理中立结构。

OS 可以组织外部变化接纳、输入/身份/权限校验、必要保存、App 安装和可用性入口、Provider/Connector/进程生命周期、资源及启动机会，并接回 Core 结果交给对应外部系统。组件负责具体存取，骨干保持薄；管理环境不是替主体作判断。

Scheduler 若实现，只管理检查、交付时机、配额、排他、退避/重试与服务恢复。不判断内容重要性、不排序任务、不生成摘要/人生计划、不伪造主体已读，也不把调度原因当认知。

## 4. 接口与领域行为

数据接缝传递 Fact、View、ActionResult、Observation、Outcome；能力接缝提供模型、行动、账本、恢复、时间等机械能力。二者不能合成“构建视野并运行 App、写效果、收场”的万能 Host。列出能力方向不意味着预先冻结所有 Port 名称和签名。

Core 领域对象拥有自己的状态与不变量；流程引擎组织读取事实、调用模型/动作、保存与返回的顺序。引擎不能绕过领域对象改状态；领域对象不偷偷调用网络、文件或模型。

对象只有在行为改变自己拥有的状态、受自身不变量约束、不理解具体 App、无需直接外部 I/O 时才拥有该行为。Run 管轮次、经历及终态；Effect 管身份、准备/派发/结果/结算；Agent 执行实例管身份绑定和活动资格，不直接拥有 Email、IM、Provider、Notification 或文件系统。

Composition 可以持有长期设施，也可每次活动建立借用作用域；持有同一个对象不是全局唯一性。谁能创建执行实例、取得同身份写权必须有独立机制。

替换 Provider 不改变 Run/Trace/Outcome/Ledger；替换组件不能破坏能力发现、参数、授权、来源、结果分类、追加顺序或生命周期承诺。实现不支持某种翻译就明确失败，不暗造兼容分支。

## 5. 状态归属与存续

| 内容 | 权威归属 / 生命周期 | 使用边界 |
|---|---|---|
| 身份记录与环境关联 | Foundation 定义身份语义，环境明确归属；跨 Run/重启 | 调用声明只供核对；模型自述、相同字符串或普通对象不授予执行权 |
| 自身说明与设定 | Agent 专属设定和共享系统规则分开；显式修改前保留 | 修改权由授权契约定，不推定主体可改全部设定 |
| system 协议包装 | Composition/Adapter 按当前契约生成 | 可重建，不保存供应商 system 消息充当身份权威 |
| 活动占用、Run/Turn/终态 | Core 执行实例及本次 Run | 外层不能清槽以并行开同身份活动，不代判任务完成 |
| 初始输入、活动 Trace | Core 本 Run；按执行可靠性契约增量确认 | 接缝只追加；Provider 读 View，不产生第二份可变历史权威 |
| View、展开标记、临时调用状态 | 本 Run / 本轮 | 回收后不作下次权限或记忆来源；能力撤销不抹去既有经历 |
| 已结束 Trace、主动笔记/交接 | OS 历史责任面与相应 App 分别保管；目标跨重启可查 | 查阅形成新观察；不自动全量继承/摘要；保留期限与授权删除另定 |
| 操作与确认事实 | Foundation Ledger 规则，单主体归属 | 存储适配兑现耐久；不从经历摘要猜效果 |
| OS 配置、通知/已读、闹钟 | 按 Agent 隔离，持续意义状态目标跨 Run/重启 | 临时连接/统计可重建；游标、到期、已读语义须定具体契约 |
| App 账户、原始数据与设置 | Agent/App 或外部权威 | 不随 Run 清空，不复制为本地第二公共权威；通知只引用/投影必要信息 |
| 权限与凭据 | 授权事实和凭据材料分开、归属明确 | 重启不扩权；凭据可轮换/过期，不写 Trace；历史权限不覆盖当前契约 |
| 唤醒资格、待启动请求 | OS 明确政策 | 忙时不强开第二 Run；保留/合并/撤销另定 |
| 进程、模型客户端、网络连接 | Composition/OS 持有，可重建 | 重建不是重建主体或自动重放操作 |

不同事实不因方便共用无限容器。Ledger、Trace、App Data、Diagnostic Log 各有用途；具体存储方案不能由这张逻辑表推出。

一个 Agent 私有事实任一时刻只有明确的可写执行者；公共世界仍只有被授权的公共写者。多 Agent 可共享设施代码，不共享私有身份、事实、操作、凭据、App 状态和活动。环境排他与跨目录同身份全局唯一性是不同保证。

## 6. 生命周期与新 Run 的处境

| 时刻 | 责任与流向 | 不得冒充 |
|---|---|---|
| 启动环境、暂无 Run | 校验身份/执行权，构造设施，接纳必要信息，等待机会 | 环境在线不等于主体思考 |
| 外部变化 | App 保存业务信息，通知组件按规则形成提示 | 每条变化不必通知、每条通知不必唤醒 |
| 提供启动机会 | OS 请求 Core，执行身份/占用/资源检查 | 拒绝启动不等于主体作了选择 |
| Run 建立 | Core 登记、初始输入、Run 注入，准备首轮 | 登记不是已经思考 |
| 每轮 | Turn 注入 → 当前能力/View → 模型 → 动作及结果或结束 | 钩子不改历史、不执行、不定终态 |
| 新通知到达 | 状态栏给机械事实，主体按需看通知/App | 不强制打断、切页或隐藏旧正文 |
| 结束及保存 | Core 如实终态，按增量保存契约结束与封存 | 资源耗尽/保存失败不作任务完成或历史完整 |
| 下一次 Run | 新 Run、新 Trace，环境持续；主动查询旧经历 | 不自动接续、重放或代写交接 |

开场通过当前有效配置及授权确认身份/环境，Run 接缝提供必要身份说明、明确输入、环境入口和真实启动原因，不预建固定大提示模板。能力、权限与资源状态只能用当前可核实事实。通知正文、App 数据、旧 Trace、笔记及交接默认在环境中按需读；调用方显式提供为输入时标来源，不能偷偷自动接续。开场文本、历史系统规则均不能提升当前权限。

外部断连、Provider 不可用、App 错误、调度取消、崩溃和保存未知须分层诚实报告。OS 可重试安全机械操作，不能在未知时猜效果；可靠性事实归 Foundation，Run 边界归 Core，业务事实归 App/外部系统。

## 7. 工程验收与待决边界

每个模块须说明所属层、事实/不变量、依赖契约及实现者、失败/Unknown、恢复边界、是否泄漏业务，以及删除后失去的真实必要能力。不能回答就删除设想或暂缓，不靠加抽象掩盖。

不采用巨大 Coordinator/Context、按来源多套循环、全业务万能 App 接口、Provider 类型进入 Core、用字符串暗编码 App 业务控制流程、自动长期记忆容器；中立能力标识本身不等于上述业务编码。

持续性验收应跨真实进程：进程 A 打开明确环境、Run A 增量保存并结束；进程 B 校验同身份/环境、开新 Run B，开场不含 A 全正文，主体经真实能力目录主动查询 A。还须验证身份隔离、第二写者、重复/未终结 Run、每个保存失败点、未确认效果与封存失败，不以同对象两次调用或直读存储替代产品能力证明。

当前未完成项以 README 为准；待明确的工程契约包括多 Run 恢复与 Unknown 调查、忙时启动请求、通知/闹钟恢复、精确资源容量、全局身份执行权、存储损坏处置/加密/保留期限。它们不是下一刀承诺或自动授权。旧 Runtime 不因新架构获得迁移/删除义务，冻结公共协议不变。
