# Celira Project Shape

> 状态：宪法级形态判据
>
> 本文回答 Celira 这个项目**由几个发布单元构成、每个单元对用户承诺什么、它们之间靠什么保持一致**。
> 它不描述实现细节（那些归代码与各组件 README），不新增公共协议，也不覆盖冻结契约。系统地图见 `ARCHITECTURE.md`；打包机制见 `scripts/make_release.ps1`。**本文不引用施工报告**：判据与证据一律落在活文档与源码行号上（考古走 Git 历史）。

## 1. 第一性原理：发布单元与使用方式是两根轴

**发布单元**回答四个问题，全是分发问题：一次拿多少东西、谁声明版本、依赖怎么解、签名与校验的单位。
**使用方式**回答另外的问题：装在哪台机器、跟谁同源、谁先起、谁备份谁。

两根轴**不一一对应**：一个包可以支撑多种使用方式（一个二进制，单机与分布式都是它），多个包也可以只对应一种使用方式（几个包装在一起才成为一个可用的东西）。

**唯一真正把两根轴绑在一起的是版本同步。** 因此发布决策的实质是：

> **我们愿意替用户承担多少兼容性责任。**
> 一个包 ⇒ 承诺"装上的东西一定互相兼容"，代价是发版粒度被绑死。
> 多个包 ⇒ 兼容性由文档与测试承担，代价是必须写出并验证那些规则。

## 2. 判据：什么时候该切出一个发布单元

四条全过才切；有一条不过，就不切。反向红线：**每切一个单元就多一份版本声明，缝越多，承诺越贵。**

1. **可剥离** —— 剥掉它，另一边是否仍然完整？（"换掉"是否对称）
2. **版本独立** —— 它与对面之间是否存在**独立的版本轴**（协议或格式）？没有独立版本轴的东西切出去，只会得到两个永远同号的包。
3. **生命周期独立** —— 是否在不同机器上、以不同频率重启、有不同的备份与信任边界？
4. **平台独立** —— 是否可能只为其中一个平台单独构建它？

**推论（比判据本身更常被用到）**：

- **发布单元的数量可以与"能独立部署的进程数"无关。** 多个可独立部署的进程住在一个发布单元里是主流做法（自托管产品普遍如此），不是例外。
- **"能独立部署" ≠ "能独立启动"**，它是两句：**A 能独立启动**（不依赖另外两个单元在场）与 **B 能对外接上**（能指向远端的对方，而不是只能找到本机的同一个家）。**只满足 A 不满足 B 的发布单元是废的**——用户下载了、起来了，却发现只能连自己。
- **中心必须能单独活；外围可以缺席；外围必须能指向远端中心。**

## 3. 当前形态：三个发布单元 + 一个 app

| 发布单元 | 对用户的承诺 | 判据依据 |
|---|---|---|
| **world**（`celira-core`） | 装了就能当一个世界（单写者、含它自己的部署文档） | 可剥离（换成别的 IM，执行端照旧活）；版本独立（Core v1）；生命周期独立（在服务器上，由你运维） |
| **runtime**（`celira-home`） | 装了就能当一支执行端，可装 N 支，可上服务器 | 可剥离（世界不关心谁在跑 Agent）；版本独立（独立 crate）；生命周期独立（在你自己的机器上）；**平台独立（服务器是 Linux）** |
| **all-in-one**（`celira-<version>`） | "懒得配"的一条路：三个部件一次装齐 | **不是第四个部件**：它不拥有任何事实，只是便利入口 |
| **app**（Tauri 壳） | 呈现平面 + 总控台；**不是发布单元**：它是同一份客户端代码的另一个壳 | —— |

**当前只发布 all-in-one 那一个 zip；两个子包与前端包已装配但只落盘，等发布渠道裁决**（`scripts/make_release.ps1` §5 注释）。

## 4. 前端不是发布单元

前端（`client/`）是**一份构建产物**，被"谁 serve 它"的那一方带着：all-in-one 带一份、world 带一份（因为它要 serve 自己的页面）、app 壳包一份。**它不是货架上的第三件商品。**

判据：**一个纯静态站点单独下载下来是没法用的**——它必须有人 serve，而那个 serve 它的人必须能代转到世界（`/v1` HTTP + 两条 WebSocket + `/home-status/*` + SPA 回退）。所以前端永远是"被带着"，不是"被下载"。

**一条硬要求（app 分发的生命线）**：**世界地址必须由运行时提供，绝不编进构建产物。** 一份构建连任意世界；一旦为某个部署把地址打进包里，前端立刻退化成"每个世界各构建一份"。

**同源是运维便利，不是架构约束**：web 页面在世界自己那台机器上被 serve（或由统一域名的反代收在一起），是为了"打开地址就能用"；不是因为架构要求它们必须在一起。

## 5. app 是总控台，服务器不出界面

**双平面的呈现归 app**：app 同时持有两条数据通道——**世界通道**（绝对地址 + Human token → 世界的 `/v1/*`）与**家通道**（绝对地址 + 家钥匙 → 那台机器的 `/home-status/*`、`/home-config`），家通道可加 N 条（本机一条 + 每台云机一条）。

**为什么服务器上不该出 dashboard**：世界与执行端可以摆在不同机器上，**任何装在某一台机器上的界面都只能看见同一台机器的那一半**。只有用户手上的 app 能同时看见两个平面。这不是偏好，是形态推论。

**app 的壳选 Tauri，请求走 Rust 侧发出**，因此浏览器的同源策略不参与 app 路径 ⇒ **世界不需要为 app 新增任何跨源面**。判据一句话：**发请求的那只手是 Rust 还是 webview**——是 webview，跨源规矩就还管；是 Rust，就与它无关。

**世界里"必须上机"的只有一件事**：operator CLI（`bootstrap-human` / `create-human` / `issue-human-session` / `issue-pairing-grant`）要直接接触 SQLite 文件，**没有远程管理协议**。开天辟地那一次只能在服务器上做（这是有意的安全设计：若"创建首位 Human"可在网络上做，从部署完成到首次登录之间就是一个抢占窗口）。此后远端能做完剩下的一切，包括**创建 Agent 与签发凭据**（`POST /v1/agents`、`POST /v1/agents/{id}/backend-bindings` → `.../credentials`，认证为 Human Session）。

## 6. 版本责任：一个发布 = 一个版本号

**三个发布单元带同一个版本号，一次装配，一起发。** 用户只有一个号要记，不需要思考"我该下哪个"。

**机械守卫现状**（`scripts/make_release.ps1`，不一致即 exit 2，不会产出混版包）：`tag == v<根 Cargo.toml 的 [workspace.package].version>`，且 `agent/Cargo.toml` 的 `version` 必须相等。
**还剩一处缺口**：`client/package.json` 的版本是 `0.0.0`，不在对账里（前端不是发布单元，见 §4）。⚠ 原先登记的第二处——「发布包目录名 / tag 与 `agent/` 版本可以互不相等」——**已由脚本收口**：`scripts/make_release.ps1` 对 `$Tag -ne $expectedTag` 与 `$agentVersion -ne $version` 各有一道 exit 2。

**协议版本只做运行时的兼容判据，不当发布绑绳。** 版本号管发布，协议版本管运行，两者不互相冒充。

**不引入版本协商、能力清单或降级矩阵**：四条边界今天都没有"第二个版本"的实现，现在写协商就是为想象中的未来建设。**当务之急是把已有的"静默坏"改成"说出口"**（诊断读数属新公共面，须裁）。

**一条日常可达的风险**：`node home.js up` 是幂等的，且**不重启已在跑的 core 与宿主** ⇒ 换了二进制之后旧进程照旧在跑，**新旧混搭在日常使用里可达**。装一套新包、跑一台旧进程，比装一个混版包更容易发生；这是版本责任的真实边界。

**换包是普通命令，不是子系统**（2026-10-12）：**停 → 换 → 起**，**回退点就是上一个包**（包留着，换回去即可）。
判据两条，都是"别耦合"的推论——① **部署目录是它自己的一个普通目录**：不在构建产物目录里（打包器每次整份重写自己的输出目录，线上那份住在里面就等于给自己写了个没人知道的过期时间），也不是指针/junction 链（那条链会要求每一处路径比较都懂"链接、8.3 短名、替代名"，是为省一次拷贝买来的一整类坑）；② **机制不认识执行者**：主人、她（她有整机全权的命令行）、一个 `.cmd` 跑的是同一组命令——**凡"谁在升级、什么时候升级"变成机制要知道的事，那个设计就已经耦合了**。
两个"不做"跟着这条一起来：**不做更新器框架**（没有第二个消费者），**不做运行中自替换**（Windows 锁着正在跑的 exe；而且世界与住户是壳起的——"谁起的谁停"）。**重启这一下必须有外面一只手，那只手就是壳**，它不需要为这件事新增协议。
同族一格：想在换之前先试，就用**另一个家**起一份测试实例（**环境变量 `CELIRA_HOME_DIR` 指到那个家**再 `node home.js up`——**`up` 不收 `--home`**：那一格是常驻件自己声明"我属于哪个家"用的，命令写法见 `scripts/HOME_MANUAL.md`；它自己的口、自己的主人、自己的世界）。**判据是数据**——那个家里没有正式数据 ⇒ 它是测试数据，不是"第二份她"（`AGENT_CONTINUITY_CONSTITUTION.md` §五：连续性是**数据**的属性）。

**更新只换程序，不动用户数据**（尽可能地；2026-10-12）：**"更新"的定义就是这件事**——换掉程序，留下数据。所以"尽可能地"有一半是**结构性**的：**程序目录与数据目录必须是两个地方**（部署目录是它自己的一个普通目录；家是 `<家>`）。只要程序住在数据目录里、或数据住在程序目录里，"更新不动数据"就不可能成立——打包器一次整份重写就够把它们一起换掉。
数据唯一会动的地方**不是"换"那一步，而是"新程序第一次启动"那一步**（im 服务端启动时自动跑 SQLite 迁移，sqlx 幂等＋checksum 校验，见 README 的 `up` 一节）。⇒ 两条跟着来：① **换之前先 `node home.js backup`**——不确定这一包要不要迁移时就备：它是现成的、便宜的，**比造一个"这一包有没有新 migration"的检测器更主流**（那种检测器就是为想象中的未来建设）；② **回退 = 换回旧包 ＋ 把 backup 放回**（新程序跑过迁移时）／**纯粹换包**（没跑过迁移时）。
⚠ 与"首装"分开：`up` 对**还没布置过的家**会**布置**（造主人、造 Agent、开房——那是**造数据**，属首装不属更新）；对已布置的家它只补缺失目录、刷新随包手册、跑迁移。**别在真家上跑首装那一步。**
项目在这条上已经选了最保守的立场：**没有升级桥、schema-only、不搬行**（`CORE_V1_IM_CONTRACT.md` 的迁移纪律）——数据非动不可时，它宁可"世界从头开始"（`home.js` 的重新奠基），也不悄悄改写用户的数据。

## 8. 本机进程与托盘（app 的直觉口径）

**判据来源**：2026-09-29 主人裁决 —— 「符合用户直觉就行了」+「一台机器可以跑多个 agent」。本节把这两条推成可执行的判据。

### 8.0 一台机器可以跑多支 Agent（2026-09-29 主人裁决）

**判据来源**：`AGENTS.md`「执行点是承载一个或多个隔离 Agent 执行端的机器或部署位置」——**一个或多个**是架构原话；本条把 V1 的实现限制（一个家一支）解开。

**第一性原理**：**隔离的事实单位是 Agent，不是机器。**

| 量 | 机器级（一台机器一份） | Agent 级（一支一份） |
|---|---|---|
| 可执行件 | ✅ `celira-im` / `agent_run` / … | —— |
| 模型清单与绑定 | ✅ 哪台机器上有哪些钥匙 | ✅ 这一支用哪一条 |
| **手**（外部 MCP server 与终端档） | ✅ **家级默认**（`home.conf` 的 `mcp_*` / `terminal=`） | ✅ **一支可以覆盖**（`agents/<支>/agent.conf`：`mcp_*` / `mcp=none` / `terminal=`） |
| **身份**（`identity.json` 的 `{agent}`） | ❌ | ✅ **一支一个环境根** |
| **私有状态**（经历、记忆、笔记、活动槽） | ❌ | ✅ **绝不与第二支共用** |
| **凭据**（那只 Agent 在那个世界的后端凭据） | ❌ | ✅ **一支一份** |
| 家钥匙（照看这台机器） | ✅ **按机器发**（`home-key.js` 原文：按机器发、不是身份） | —— |

**⇒ 推论三条**：

1. **`<环境根>` 从"这台机器的那一支"变成"一支 Agent 一个环境根"**。一支 Agent 换机器 = 把它的环境根搬过去，**另外几支不受影响**——交换性由此而来。**已真机验过（2026-10-01 第七刀；读数：`outputs/_knife7-move-acceptance.out`）**：把一支的环境根整份复制到新家、并带上她那支后端凭据 ⇒ 新家把她当**已安家**（不新建、不认领；显式读数「住户 <id>（<显示名>）已安家：房 <room_id> —— 不新建、不认领」），身份与房间与基线逐字相同、带着旧经历、在**原来那间房**真回话；老家留下的另一支不受影响。**未覆盖（如实登记）**：① **真跨主机**（网络 / OS / 凭据分发——本刀是同一台机器上两套端口模拟）；② 搬到**另一个世界**并保住身份（世界侧没有这条迁移语义，今天只会「不在这个世界里」停手）；③ `node home.js backup` 那条路；④ **同一支两地同时 up**（世界对同一支只留一支有效凭据——同时跑会互相顶掉，搬家的纪律是「先 down 老家，再起新家」）；
2. **一支 Agent 一个进程**：起停的**单位是 Agent**（§8.1 的"本地执行端"由此变成 N 个可分别起停的东西）；
3. **凭据的键要从 `agent_id` 升到 `世界 × agent_id`**。`scripts/home/credentials.js` 里那套"一身份一文件"（0600）正是为此准备的，它原本记着一条 V1 限制："同一个世界的同一个 agent id 唯一"——多 Agent 之后，**同一台机器上的两支 Agent 可以住在同一个世界里**（不同的 Agent 身份），所以这一格必须带上世界的身份。✅ **已实现（2026-10-01，CLI 那条路）**：路径 `<凭据目录>/<世界摘要>/<agent_id>.token`（世界摘要取规范化世界地址的稳定摘要，**不含凭据**），读/写/轮换/删除四面一致；旧路径只作只读迁移桥。

**落地登记（2026-10-01，CLI 那条路）**：下表四格**全部已实现**，且 **CLI（`scripts/home/*` ＋ `home.js`）与壳（`app/src-tauri/src/anjia/`）用的是同一套布局** `<家>/agents/<支>/`（壳 `home.rs` 的 `agent_env_root` 是先落地的那一套，CLI 这一刀追上去，**没有第三套**）。落地读法：`node home.js up` 遍历住户各起一个宿主、`up --agent <id>` 给一支安家、`status` 按支读数、`down [--agent <id>]` 停一支或停家；住户 1 沿用**无后缀**的旧幂等键（老家在世界里的记录就是那把键建的，改形状会让它静默另建一支），住户 2 起带住户序号；凭据的键升到 `世界 × agent_id`。对外承诺见 `scripts/HOME_MANUAL.md`「一个家住多支 Agent」。

**手也按支（2026-10-01，第五刀）**：**手长在身体上** ⇒ 外部 MCP server（`mcp_*`）与终端档（`terminal=`）从家级升成**支级事实**，`home.conf` 里那些降为**家级默认**。三条规则：支级有 `mcp_*` ⇒ **覆盖**（不是合并 —— 合并会让"我要一支完全没有外部 server"变成做不到）；支级 `mcp=none` ⇒ **一只都不要**；都没写 ⇒ **跟家走**（2026-10-01 之前的行为一字不变）。**终端档（2026-10-14 主人裁；2026-10-23 加 sandbox）**：支级 ⇒ 家级 ⇒ **平台默认，而平台默认是「不给手」** —— **要 full 就显式写 `terminal=full`；要受限手就显式写 `terminal=sandbox`**（只有 Linux 且 runtime 探针通过）；`terminal=none` 是「明确不要」（家级给了、这一支要退掉时用它）。home 是产品路径，**不传旗标就是 none**（宿主的缺省档已经与产品默认一致）；只有显式 `terminal=sandbox` / `terminal=full` 才进 argv，因此明确写 `none` 的支不会被读成 sandbox。这次缺省变更带一次**一次性迁移**：`up` 开机时按**家级标记**（`home.conf` 的 `terminal_default`）把老支在旧缺省下本来就有的 `full` 显式写进各自的 `agent.conf`，幂等；此后新建的支吃新缺省。读侧（`up` 的起机读数、`status` 那一行、状态口载荷）**按支说、并说清来源**（它自己的 `agent.conf` ／ 跟家走 ／ **平台默认不给** ／ 明确不要）；状态口只给**名字与数量**，命令原文不上屏、不进载荷。

**家级常驻件的账（2026-10-01，第六刀）**：一支住户宿主空闲约 **9 MB**；家级那几件是**固定成本** —— **家的门**（只读状态口 ＋ 模型配置门）约 **56 MB**、页面托管 **60.3 MB**（源码形态从前走 `vite preview`，同一份 `client/dist` 实测 **122.7 MB** ⇒ 已换成**与发布形态同一条** `scripts/serve_client.mjs`；vite 只在**构建**那一步出现）、世界约 13 MB。⇒ **住户越多、人均越便宜**（3 支：宿主 27 MB，家级件约 130 MB）—— "省内存"的杠杆在**家级件的数量与寿命**，不在住户宿主。

**两个门合成"家的门"（2026-10-01，第六刀，主人裁"别被以前的文档束缚，要合理"）**：只读状态口与模型配置门从前是**两个进程**（各 ≈56 MB，共 112 MB/家），现在是一个进程的**两个端面**（≈56 MB/家）。判据不是"省内存"，是**它们服务同一个读者**（本机页面，走同源代转）、**同一个寿命**（页面在不在跑）、**同一句恢复话**（重开一次 `up`）：分开只买到"一个崩了另一个还在"，而用户能做的还是同一件事，代价却是每个家多一个 Node 进程 ＋ **一整套重复的**启动 / 探活 / 账本 / 日志 / 关停 / 归属判据（`proc.js` 里那两条互相提防"认错进程会去杀错人"的跨词短语就是这套重复的化石）。

**合并的是"谁在听"，不是"谁能被谁访问"** —— 端面一条没合并：两个端口（读 `status_port` / 写 `config_port`）、两张**逐条列出**的路由表（读端面只有 `GET /status` ＋ `GET /healthz`；写端面只有那几条配置路由，互不串门）、两套准入（读端面可绑远程 + 家钥匙；写端面默认只本机）。两条故障纪律：① 两个端面**各自绑定** —— 一个口被占不许把另一个拖下水；② 一个端面**不许**因为另一个在同一个进程里就放行/降级访问控制。旧形状（两个进程）的两本账与两条指纹**留作迁移桥**：老家还跑着旧门时 `up`/`down` 认得出、收得掉。

**将来该重新分开的触发条件**（写在契约里，免得下次只剩"历史决定"）：① 写端面也要对**不受控来源**开放（那时读写同进程会成为越权面）；② 门里的逻辑长到"一份代码的崩溃概率不可忽略"；③ 出现"读口必须在写口坏掉时仍可用"的**真实运维需求**（例如托管服务要承诺状态可观测性）。另两条已裁过的边界：**不做住户宿主的闲置退出**（它自己维持世界唤醒流；替它守门的人就得持这一支的凭据 ⇒ 扩信任面，或改世界契约 ⇒ 违反"世界那侧一行不改"）；状态口的多支探测**并行**（每支一次 `agent_host_status`；串行会让 3 支的页面刷新线性变慢 —— 三支各 80 ms 的慢探测替身：串行实测 244 ms → 并行 83.9 ms）。

### 8.0.1 住户之间的隔离到哪一档（2026-10-01 主人裁决）

**判据**：**隔离的边界画在"信任域"变化的地方，不画在住户之间。**

一个家的住户是**同一个主人**的几支 Agent；而一支 Agent 拿着 `--terminal full`，跑的是**主人的 OS 账号** ⇒ 它本来就看得到主人的一切（SSH key、浏览器数据、主人自己的 token）——**那些都比邻居的环境根值钱**。在自家院子中间砌一堵墙：安全收益≈0，维护成本>0。

**平台事实（比上面那条更硬）**：§9.1 裁的第一平台是 **Windows 完整 app**，Linux 只是"world + runtime 两个包、用户自己部署"。**Windows 上没有 uid 这个概念** ⇒ 住户级的硬隔离要么上 AppContainer / 独立本地账户（重、要管理员权限），要么不做 ⇒ **平台分叉**：同一个词在 Windows 上只是"防故障"、在 Linux 上变成"防越权"。**同一句承诺在两个平台含义不同，比"承认不防"更坏。**

**⇒ "隔离"在 Celira 里的准确含义（两档，别混着用）**：

| 买到了 | 没买到 |
|---|---|
| **防故障**：一支崩了 / 跑飞了 / 卡死了，别的住户与世界不连坐（进程边界 ＋ 一支一份账本与日志） | **不防越权**：同一个 OS 用户下，一支用终端读得到另一支的经历、笔记，甚至那支的后端凭据文件 |
| **防误共享**：身份 / 私有状态 / 后端凭据**按构造**不会被两支共用（一支一个环境根；凭据键带世界与身份） | —— |
| **可分别起停**：停一支不动世界、不动别的住户 | —— |

**判据（承上）**：**对自主的 Agent，限制不可能"限全"** —— 它的动作空间无法穷举（这正是"自主"的意思），所以枚举式的白名单与沙箱只能挡住**已知**的那些。⇒ **可控性来自"看得见 ＋ 撤得掉"，不来自"墙"**：

- **看得见**：每一步活动都写在 `<环境根>/trace.ndjson`，主人读得到；`status` 按支读数、状态口按支给载荷；
- **撤得掉**：凭据被撤 ⇒ 门铃**下次发送前重认证**、断流 fail-closed；起停的单位是 Agent，随时能掐。

**四条触发条件（出现任一条，要么补墙、要么改宣称）**：

1. 住户**不再属于同一个主人**（多租户 / 别人给的 Agent）；
2. 一支的**手来自不受控第三方**（外部 MCP server、别人的技能包）——那时它是"可能主动偷东西的"。
   ✅ **配置层已经分得清**（2026-10-01 第五刀：手按支声明，读数按支说清来源）⇒ 触发时**先按支关掉那只手**（`mcp=none` / `terminal=none`）或**停那一支**，不必动别的住户；
3. 对外宣称里出现"**安全隔离 / 防越权**"这类词；
4. 家被搬到**共享机器**上，且世界对多主人开放。

> **不做的那件事，理由也要写下来**：不按敌手隔离做，不是"省事"，是**边界画错了地方**；真正的安全边界（主人的 OS 账号）今天已经由操作系统给了。要补的那一天，补法也清楚：per-resident uid / namespace / 只读挂载——**世界侧与契约一行不用改**，只改"起宿主那一下"的编排与一份权限清单。

### 8.1 两类东西，两个归属

| | 谁拥有它的生死 | 关掉本地 app 会怎样 |
|---|---|---|
| **本地世界**（一个） | **这颗本地 app**（它的子进程） | **跟着停** |
| **本地执行端**（一支 Agent 一个进程，可 N 个） | **这颗本地 app**（各自的子进程） | **跟着停** |
| **云上的世界 / 云上的执行端** | **那台机器**（systemd / 服务 / 你手点） | **完全不受影响**，只断开连接 |

> **判据**：停止动作的**作用域 = 这台机器**。远端的东西只断开，**绝不改变它的运行状态**。
> ⚠ 这条最容易被"一键全部停止"这种便利功能写坏 —— 那样用户点一下会停掉**别人的共同世界**。
>
> **推论（承 8.0）**：本地执行端是 **N 个可分别起停的进程**，不是一个。"停一支 Agent"与"停世界"是两件事 —— 停掉一支，世界照旧服务其他人。

### 8.2 托盘是界面便利，不是进程寿命机制

| 动作 | 结果 |
|---|---|
| 点窗口的 × | 窗口收起，**app 还在托盘**，本地进程照旧跑 |
| 托盘菜单「退出」 | 本地进程跟着停（它们的出身就是这颗 app） |

**托盘解决的是"界面关了但 app 不退"，不是"进程活得比 app 久"。** 因此**不需要**把进程做成脱离父子的守护进程，也**不需要**"认领进程"（PID 认领）那套逻辑（见 8.7）。

> ⚠ **一个术语冲突，先在这里拆掉**：仓库里 `scripts/home/adopt.js` 的 `adopt` 指的是**把一支 Agent 接到一台机器上**（世界侧身份 ↔ 机器侧身体），与本节的"**认领进程**"（认领一个已在运行的 PID）**是两件完全不同的事**。本节把后者叫「**PID 认领**」，前者叫「**安家**」（见 8.5）；写代码与文档时别用一个词指两个东西（`AGENTS.md`「统一语言」）。

**一条必须一起做的**：**托盘图标要能看出"还有本地服务在跑"**。否则用户会以为已经全关了，而东西还在后台写磁盘、占端口。

### 8.3 退出语义（用一次明确表态解决"用户预期"）

- **托盘菜单里写清后果**：菜单项叫「退出（停止本机服务）」，**把后果写在菜单项上**，而不是退出后弹一句解释；
- **面板上给总开关**（`[全部停止]` + `退出时：[保持运行 ▾]`）——"只想留壳子"的用户一次点击就能做到，并且知道自己做了什么；
- **默认值**：不替用户做隐蔽的事。

### 8.4 家的管理模型：地址与凭据归 app 管，服务器归用户管

**一条家条目 = 一条地址 + 一把可选的钥匙**，就这一个形状。

| 条目 | 地址 | 钥匙 | 谁填 |
|---|---|---|---|
| **本机**（预置，不可删） | 约定地址（`127.0.0.1` + 约定端口） | **不需要**（loopback 落在 `home-key.js` 的**模式一**：免钥匙、无 TLS —— 今天就是这个行为，一个字不用改） | **app 自己知道**（世界是它起的，端口是它选的）—— 用户永远不用填 |
| **远程**（用户加，可多条） | 绝对地址（**必须 TLS**） | **家钥匙必填** | 用户填（在那台机器上 `node home.js issue-home-key` 拿到） |

> **判据**：**用户负责"那台服务器"（开、部署、保持活着）；app 负责"怎么连它"（地址、钥匙、条目）。**
> 让用户去记本机端口、自己发本机钥匙，是把**我们**的实现细节摊派给他 —— 那不是"让用户自己处理"。

**"符合第一性原理"的三个推论**（承 8.0）：

1. **家钥匙按机器发**（`home-key.js` 原文：按机器发、不是身份），**所以多支 Agent 不增加钥匙**；
2. **本机地址由 app 解析** —— 这也把先前那条"相对路径在壳里响亮失败"从缺口变成正常路径（壳里唯一能解析相对路径的 base，就是本机世界）；
3. **远程条目不做"同域反代省钥匙"那条捷径** —— 多一层运维换一把钥匙，不划算；家钥匙本来就是 possession 证明，与 Human token 同类。

### 8.5 安家：app 必须补上这条洞（今天产品上最大的那个）

`scripts/home/adopt.js` 自己写着：世界侧能建 Agent（`POST /v1/agents`），但那只建了**身份** —— 不写配置、不发后端凭据、不起任何东西 ⇒ **她不会回话**。**v1 里缺一条把「世界里的她」与「这台机器上的身体」接起来的路**——机器侧只有 `adopt` 那条窄路（只通"这个家还没有住户"的场合，2026-09-27 落）；**缺的是 app 里这条**。

**术语**：这一步叫「**安家**」（把一支 Agent 接到一台机器上）；与"PID 认领"（认领一个已在运行的进程）无关，见 8.2 的术语说明。

app 里这条路必须是自动的（**否则"在 app 里创建了 Agent，她却不回话"**）：

```text
用户在 app 里「创建 Agent」
  → POST /v1/agents                            （世界侧：建身份）
  → app 自动安家：GET /v1/agents 核实"这个 id 是我的、且 active"
  → 建它的环境根 → 写它的身份 → 签后端凭据 → 起它的进程
  → 她开始回话
```

**`adopt.js` 的三条判据照抄**（它写得对，只改第三条）：

1. **只能认领自己的**：id 必须在**你拥有的** Agent 列表里，且 `status` 是 `active`（撤销过的不许安家）；
2. **问不到就不动**：世界连不上 / 回执读不懂 ⇒ **拒绝**（绝不先写上、回头再说）；
3. ~~**一个家只住一支**~~ → **改成"这支 Agent 是否已经安家"**（承 8.0：一台机器可跑多支；同一条判据的意思从"这个家有没有主"变成"这支有没有家"）。✅ **已实现（2026-10-01，CLI 那条路）**：`node home.js up --agent <id>` 就是这条支级判据 —— 已有 ⇒ 幂等重跑它；没有 ⇒ 认领成新住户；家里已有别的住户不挡路。

> **判据（2026-09-30 立，承「双平面」）**：**不存在默认 Agent** —— 一支 Agent 的诞生 ＝ 世界侧一次**显式创建** × 机器侧一次**显式安家**；机器不会自己冒出一支；第一支与其他支走同一条路（承 8.0："先来后到"不成立）。

### 8.6 三条配套判据

1. **第一次启动问一次**"要不要在这台机器上跑一个世界"（它会写磁盘、占端口、常驻后台）；之后按面板的开关来；
2. **用户停过的，重启 app 不许偷偷又起来**；进程自己崩了**不自动重启**（自动重启会掩盖真实失败，如端口被占或库损坏）；
3. **首次布置自动做**（建首位 Human、签凭据、开值班室）——要求用户先跑一次命令行就违背了 8.1 的直觉口径。**这一步不需要新契约**：world 二进制自带 operator CLI（`bootstrap-human` 那一族），今天的 `home.js` 就是调它完成的；壳里照做即可（起一次子进程、收一份 JSON）。

### 8.7 因此这一格的工作量比看上去小

- **不需要**进程发现与 PID 认领 —— `scripts/home/proc.js` 里最重的那一块（`listProcessesByName` / `homeFlagVerdict` / CIM 查询，34 KB 里的主体）**在简化模型下整块不要**；
- **不需要**与云上部署冲突：云上归 systemd，壳根本不参与进程管理；
- **剩下要搬的**：调 operator CLI + 起停子进程（世界 1 个 + 每支 Agent 1 个）。

### 8.8 验证边界（先标出来，别当已完成）

**托盘能不能出现、菜单能不能点，无法用程序读出来**（托盘不是窗口，不像主窗口那样能读标题与句柄）。⇒ 这一格的分工是：**代码侧做到"编译通过 + app 能跑"**，**托盘本身要真机点一次才算验过**。

## 9. 构建环境与平台矩阵

**一条实测结论（2026-09-29，更正过一次）**：**壳能编译、能开窗口 —— 但这不等于壳能用。** Tauri 桌面壳（`app/`）实测已通过：`cargo check` 67 s、`cargo build` 82 s 出 24.2 MB 产物、运行后窗口标题 "Celira"、WebView2 子进程正常、关闭无残留。

**先前那条"本机拉不到 crates"的结论不准确**：逐项复测后，索引端 `index.crates.io` 可达、下载端 `static.crates.io` 可下载（serde 79 KB / 1.0 s）；**真因是网络抖动叠加 cargo 默认 30 s 超时太短**，把超时放宽后依赖 253 s 拉完。⚠ **`.cargo/config.toml` 不进仓库**——它会覆盖使用者自己的镜像设置；本机那个指向连不通镜像的全局配置，修它属**本机运维**。

**两条独立的卡点，别混为一谈**：

| 卡点 | 性质 | 解法 | 现状 |
|---|---|---|---|
| **crates 源抖动** | 网络 / 镜像 | 放宽 `CARGO_HTTP_TIMEOUT` / `CARGO_NET_RETRY`（见 `app/README.md` §6） | **已绕过**（本机实测可编译） |
| **macOS 只能在 macOS 上构建** | 平台工具链 | Mac | **未解** |

### 9.1 目标的平台集（2026-09-29 主人裁决）

**初期只做两样：Windows 的完整 app + Android 的纯壳。**

| 平台 | 要什么 | 状态 |
|---|---|---|
| **Windows** | **完整 app**：壳 + 本机世界 + 本机执行端 | 在做（§9 前置依赖第 3 步） |
| **Android** | **纯壳**（只能连远端，见 §9.3） | 未开始 |
| **Linux** | **不要壳** —— 只要 **world + runtime 两个包**，用户自己部署（一般是自己那台服务器） | 打包侧已参数化；产物已在 Linux 本机产出（2026-09-30：all-in-one ＋ 三个子包；发布渠道未裁，§7 缺 3） |
| macOS | 桌面推后 | 未开始 |
| iOS | **不做** | —— |

**Linux「不要壳」不是省事，是形态本来就不同**：在 Linux 上跑服务的人用命令行（`home.js` 那一套），要界面时 **web 版今天就能用**（world 自己 serve 页面）。

> **判据**：**Linux 缺的是"构建"，不是"新形态"**（构建 2026-09-30 在本机跑通，见 §7 缺 3）。`celira-core` / `celira-home` 就是前面定的两个发布单元（§3）—— Linux 这一格**没有需要新做的东西**，只是把已有的两个包在 Linux 上编出来。
>
> 这条同时**消掉了一个伪问题**：不必设计"Linux 桌面壳"。而它之所以不损失什么，正是 **§4「前端不是发布单元」那条判据的红利** —— 不发前端包，用户照样有界面。

**砍掉 iOS 省下的**：Xcode 工具链、App Store 流程与审核（含"这 app 能连用户自己的服务器"那类问询）、Apple 开发者账号、TestFlight 分发。
**留下的**：Android 手机壳仍要 Android 构建环境（Android Studio + SDK + JDK），**不是零成本** —— 省的是钱，不是工夫。

### 9.2 分发与签名：**开源不免这条路**

**代码签名认的是"谁签的"，与开源与否无关。** 但**不签名也能发**，代价是用户那一侧多一步。

| 平台 | 不签名的后果 | 能不能免 |
|---|---|---|
| **Windows** | SmartScreen 一句"未知发布者"，用户点"仍要运行"即可 | **可以就这么发**；另有 **SignPath Foundation 给开源项目的免费签名名额**（需申请过审）——**顺序是先免费名额，再考虑买** |
| **macOS** | Gatekeeper 拦，用户要手动绕（右键打开 / 隐私设置放行）；公证需付费开发者账号 | 源码构建天然免疫（自己编的没有隔离属性） |
| **Android** | 自签名即可 | ✅ **免费** |

> **判据**：这条成本**只落在"给非程序员分发二进制"上**。开源项目的另一条分发路径是**源码构建**——那正是许多开源项目不发预编译包也能活的原因。
>
> ⚠ **口径提醒（下次动工会做错的那一步）**：不要因为"项目开源"就以为签名与商店成本不存在，也不要因为"没签名"就以为发不出去 —— **两句话都是错的**。

### 9.3 手机壳的形态差异（不是缺陷，是平台事实）

手机操作系统**不允许常驻后台进程** ⇒ 手机壳**不能承载世界，也不能承载执行端**，只能连远的（§8 的"两类东西两个归属"在手机上退化成只有一类）。用户会问"为什么手机上开不了一个世界"——**答案是平台不允许，不是我们没做**。

**前置依赖按序**（app 为主产品 ⇒ 前端平台无关化是必答题，不是优化项）：

1. ~~**浏览器绑定收口**~~（存储 / 通知 / 传输各留一个窄接口）—— **已做主体**：`api/storage.ts`（异步窄口）、键命名空间统一（世界级 `celira.world:*` / 机器级 `celira.machine:*`）、通知面挪进 `api/notifications.ts`（治掉数据面反向依赖 hooks）、**出网收口** `api/transport.ts`（全部出网唯一经它 + 源码守卫）。**未完成**：外观两处（`use-theme` / `wallpaper`，卡在"首帧同步读"的取舍）与草稿一处；
2. **家的管理模型**（一条地址 + 一把钥匙，一台机器报几支 Agent）——平台无关，先于任何界面；
3. **Windows 桌面壳**——**已编译、已运行、出网已接线**：实测窗口标题 "Celira"、WebView2 子进程正常、关闭无残留；壳里出网换到 Rust 侧（`client/src/api/shell.ts` 由 `main.tsx` 第一行装），因此在壳里**连任意地址的世界不再受浏览器同源策略限制**，而 web 产物未被污染（插件是 1.9 KB 懒加载 chunk）。**2026-10-03 刀收了「app 里的地址从哪来」的本机那一半**：壳解析本机世界的地址与家的门两个口交给页面（§8.4 推论 2）、首次布置与「问一次」落地（§8.6-1/§8.6-3）、正门多一格 `local-ask` ⇒ **打开就在自己的世界里**；**远程条目那一半仍未做**（§8.4 那张表的后半）。**还差的**：§8 的进程与托盘（本地进程的生死归这颗 app、退出语义）、§8.6-2 的"不偷偷重启"、**起本机的执行端住户**、存储换成文件实现；
4. **Linux 包**（§7 缺 3）——即 **world + runtime 两个包**（§9.1：Linux 不要壳）；它同时让第 3 步有真东西可管；
5. **Android 手机壳**（纯客户端，另需 §7 缺 7 那条"家的公网可达"）；**macOS 桌面推后**。

**一条纪律**：**web 版只许走共用层**（`contracts.ts` / `core.ts` / `homes.ts` / `homeStatus.ts`）。今天"本机条目走同源代转、远程条目走绝对地址 + 家钥匙"是两条路；**app 里只有一条路**（家条目统一为"地址 + 钥匙"，本机那条只是地址为 loopback 的一条）。同源代转是 **web 专属的实现细节，绝不进共用层**——否则会把一条只在浏览器成立的绕行路固化进主产品。

## 10. 一句话判据（复核用）

> **包是分发单位，世界是权威单位。**
> 中心必须能单活，外围可缺席、必须能指向远端中心。
> 前端不是包，是被谁 serve 谁带一份。
> 三个单元一个号；协议版本只管运行。
> 服务器不开界面——它多开一个，就是多一个骗人的地方。
> 本地进程是本地 app 的孩子；停止只作用本机，云端只断开。
> **不存在默认 Agent** —— 身份来自一次显式创建，身体来自一次显式安家。
