# Agent Progressive Design Roadmap

> 状态：负责人交接底稿；讨论基线，不是实施计划，不代表自动授权实现。
> 修订（2026-09-12 主人裁决）：状态栏=唯一通知面（铃=按源配置）；Continuity=开场注入插槽；桌=插槽内容非核心对象；RAG=宪法判据下已否。读法校准：阶段一关系已冻结成立，阶段二（E0 装配）、阶段四（im 预装+F1/F2/F3 共五 app）、阶段五（record 家族）对应的工程现实已建成——本文用于理念校准，不是从零施工单。冲突时以宪法与终局正文为准。
> 用途：规定 Agent 设计从稳定核心向可替换扩展推进的顺序。
> 总原则：先稳定底座，再逐层增加能力；每一层都必须能被替换，不能把具体实现反向写进核心。

## 1. 推进原则

Agent 的能力可以很复杂，但 Agent 每次能看到的内容有限。因此能力和事实留在外部环境里，通过目录、入口和主动读取渐进获得。

```text
核心稳定
  -> 初始 Context
  -> 统一状态栏
  -> Extension / Tool
  -> 记忆环境
  -> 检索方式
```

不要一开始建设完整 Agent OS、复杂会话树、自动摘要体系或多级语义记忆。先证明最小关系成立，再增加扩展。

## 2. 阶段一：冻结核心关系

先只确认并保护：

- Agent 是具有持续身份的独立个体；
- 模型是无状态、有限的认知能力；
- Runtime 提供环境而不替主体判断；
- Context 是一次 Turn 的当前处境；
- Turn 是一次模型调用；
- Run 是一次有限连续清醒期；
- Agent 通过 Tool Call 推进 Run；
- Agent 行动产生 Effect，结果回到环境；
- Runtime 提供授权、幂等、取消、恢复和硬边界。

本阶段不讨论具体 Memory 分类、RAG 供应商或工具数量。

## 3. 阶段二：确定初始 Context

第一个 Turn 只装配最小输入：

```text
System Prompt
+ Tool / Extension Catalog
+ Status Bar
+ 开场注入插槽（可为空）
+ 可选临时注入内容
```

初始 Context 的规则：

- 固定身份和稳定边界来自 System Prompt；
- 可用能力来自 Tool / Extension Catalog；
- 外部变化来自通知栏（世界的账，按需拉取的完整清单）与状态栏（turn 级顶栏处境面板：世界预览 + Agent 自身机械状态——当前时间、预算余量）；
- 开场注入插槽是核心提供的固定装配通道；内容由授权来源注入（如未完结事项快照），每项须能说明来源、边界和加入理由；
- 不默认放完整历史、全部 Memory、全部工具细节或系统语义摘要。

## 4. 阶段三：统一通知栏与状态栏

所有外部动静先报到通知栏——通知栏记世界的账（app 报的动静，唯一报账面）；状态栏照自己的处境（turn 级顶栏：世界预览 + Agent 自身机械状态如当前时间、预算余量）；门铃是开机键，只决定何时开始一次 Run、不携带内容：

```text
世界变化 -> 通知栏机械记录（世界的账） -> 门铃（可选，按源配置） -> Agent 醒来 -> 睁眼=整个通知栏压缩视图+处境 -> 自己决定进哪个 app、看多深
```

状态栏可以做机械聚合：

```text
IM：来自 3 个房间，共 12 条新消息
```

但必须保留来源、类型、时间、数量和读取入口。通知栏不排序、不判断重要性、不总结、不直接塞正文。已读是逐条的：拉过详情即移除；栏满则最旧折进目录，不删除；Run 无清空通知栏义务（可带未读通知 no_reply 收工）。定时器是自己的节律，闹钟清单作为持有物躺在通知栏。醒后处理多少（一次清一批、看完不管、直接走人）全归自己决定；防 spam 分层：铃默认＝系统层、群/提及细筛＝app 层（Agent 配）、醒后取舍＝Agent。注入机制三分：开场全量压缩快照（一 Run 一次）＋turn 边界事件卡片增量（一条只播一次，游标去重——事件是历史，重播即语义错误）＋恒摆状态行（每 turn 重摆：时间/预算余量 + 各 app 未读计数「qq:10 微信:20」式，状态重摆即刷新、成本有界；Agent 处理过的消息下 turn 计数归零必须可见）。主动拉取三档渐进：计数行（免费）→ B1 卡片预览（首条预览）→ B2 进 app 全文（已读）。

本阶段验证：不同来源的变化是否能共享同一入口，而不丢失来源和可追溯性。

## 5. 阶段四：Extension 与 Tool

每个 Extension 是一个可进入的小系统；每个 Tool 是该系统暴露的原子读取或行动。

```text
Extension：维护系统
Tool：暴露原子动作
```

能力逐层呈现：

```text
主入口 -> 文件夹 / 组合 -> Extension -> Tool -> 具体事实或行动
```

（暂缓，非原则）自行整理入口的构想无真实消费者前不立项；pin 与主体命名入口已覆盖大半表达。

本阶段先用一个真实 Extension 验证完整链路，优先选择同时包含读取、行动、权限、失败和结果回流的 IM Extension。不要先做通用插件市场或自动安装系统。

## 6. 阶段五：Memory Extension

Memory 先作为一个 Agent 私有的目录式外部环境：

```text
Memory
├── Folder
│   ├── Subfolder
│   │   └── Record
│   └── Record
└── Record
```

最小能力：

- 创建、读取、移动、重命名目录和记录；
- 记录来源、时间、版本和地址；
- 浏览目录；
- 精确搜索；
- Agent 主动决定哪些内容进入 Continuity。

不预设项目、人物、工作、生活等固定分类；不自动总结、不自动归档、不自动判断重要性。

## 7. 阶段六：检索方式

目录、全文搜索和 RAG 是不同的取用方式：

```text
目录：知道大概位置
全文搜索：记得词
RAG：只记得大概意思
```

RAG（语义检索）在当前宪法判据下已否（主人裁决记录：系统不做自动语义排序、不写语义摘要），不是待评估的后续阶段；解禁须主人显式修宪裁决。

目录与精确搜索是既定取用方式；没有真实使用问题时，不引入向量数据库和复杂检索编排。

## 8. 阶段七：Handoff 与上下文续接

Handoff 是独立的临时注入内容，不属于核心；工程上经开场插槽进入 Run（handoff_notes 是未完结事项快照的组成锚点）。它只在当前 Run 因上下文边界需要续接时使用：

```text
Run A 接近边界
  -> Agent 写 Handoff
  -> Run A 结束
  -> Run B 开始
  -> Run B 读取 Handoff
```

正常结束不自动生成 Handoff。Handoff 不累计、不复制完整消息列表、不承担长期记忆职责。

## 9. 每阶段的否决条件

出现以下情况时暂停并重新判断：

- 系统开始替主体做重要性判断、分类、排序或总结；
- 一个扩展开始定义 Agent 的本体；
- 新能力只能通过某个具体模型或 Provider 工作；
- 上下文只能靠无限消息列表维持；
- 没有真实消费者却新增公共协议或复杂拓扑；
- 为了方便实现，把 Handoff、Memory、RAG 或某个 Tool 升级为核心；
- Agent 无法看见自己造成的环境变化；
- 删除某个实现后，核心关系无法继续运行。
