# Agent Core Principles

> 状态：负责人交接底稿；讨论基线，不是权威契约，不代表当前实现已具备全部能力。
> 修订（2026-09-12 主人裁决）：状态栏=唯一通知面（唤醒政策归系统服务层按源配置）；Continuity=开场注入插槽（通道归核心，内容须过来源/边界/加入理由）；桌（行动范围）=插槽内容而非核心对象；RAG=宪法判据下已否，非待评估项。冲突时以宪法与终局正文为准（权威顺序见 AGENTS.md）。
> 用途：给后续负责人快速理解 Celira Agent 设计的核心，不展开具体工具实现。

## 1. 一句话原理

> **模型提供有限认知，Runtime 提供可见环境；Agent 自己观察、判断、行动并承担结果。**

Agent 不是一次性回复函数。它是具有持续身份的独立个体，但模型本身无状态，需要输入才能产生输出，无法直接感知世界、保存长期记忆或产生外部行动。

Runtime 的任务不是替主体思考，而是为它提供：

- 可见的环境；
- 可进入的能力入口；
- 有界的 Context；
- 可持续的执行循环；
- 真实的行动结果；
- 可恢复的外部事实。

## 2. 核心与扩展

### 核心负责 Agent 如何存在

核心只保留未来很难改变、且删除后 Agent 不再成立的东西：

- Agent 的持续身份；
- 环境事实的可见性；
- Context 的装配；
- Turn / Run 的生命周期；
- Tool Call 的执行边界；
- Agent 行动后的 Effect 出口；
- 持久化、恢复、幂等、授权、取消和故障边界。

### 扩展负责 Agent 能接触什么

IM、Files、Terminal、Memory、RAG 等都是 Extension。它们可以被添加、替换和演进，不应反向定义 Agent 的本体。

```text
核心：Agent 如何存在
扩展：Agent 能接触什么
```

判断一个能力是否属于核心：

> **删除它以后，Agent 还是不是 Agent？**

删除 IM，Agent 仍然存在，只是失去通信能力；删除 Memory，Agent 仍然存在，只是失去一种记忆扩展；删除 Context 装配或 Run，Agent 将无法持续认知和行动，它们属于核心。

### 2.1 补偿与条件（2026-10-08 主人确认）

系统替主体做的机械劳动叫**补偿**；主体造不出来、只能由环境提供的东西叫**条件**。

> **模型变强只允许删掉补偿，绝不允许删掉条件。**

条件只有三件：

| 条件 | 删掉会破什么 |
|---|---|
| **首屏**（她每次醒来第一眼看见的那个投影） | 她每次醒来都要重新找自己 |
| **账**（只追加、可校验的事实） | "我做了没有"查不了 ⇒ 她的自我会崩 |
| **权威身份**（归属与世界给的名字） | 她不能自己认领自己 |

其余一切——App、工具、模型、显示件、宿主、前端——都是**可替换的**，或者必须证明自己让她**更认得出来**（可发现性）或**更核得实**（可核实性）。

判据一句话：**"模型够聪明了"不是删掉这三件的理由。**（App 尤其可替换：它提供的**能力**可以来自任何地方——内置件、一台电脑、外部来源；它不可替代的那一半是**接口**：让动作认得出来、核得实。）

## 3. 最小生命周期

```text
环境发生变化
  -> 状态栏留下机械事实（通知面）
  -> 唤醒政策按源配置决定是否响铃
  -> Agent 被唤醒
  -> Runtime 装配第一个 Turn 的 Context
  -> Agent 自己调用 Tool
  -> Tool 返回事实或产生 Effect
  -> Agent 继续、沉默或结束 Run
  -> 结果回到环境
```

通知栏是报账面，不是闹钟：栏里的内容本身没有唤醒权，叫醒 Agent 的是门铃（唤醒政策按源配置：im 这类致辞源默认响铃，fs/terminal/web 默认静默——改配置即可，不新增通道）。门铃是开机键：只决定「现在开始一次 Run」，不携带内容、不传消息、不排优先级；自己的闹钟和宿主停机不走门铃。Agent 睁眼看到的是整个通知栏的压缩视图加自身处境——触发消息没有特权，只是栏里最新的一条；详情由 Agent 进 app 查看。进哪个 app、看多深、一次清多少、看完管不管、还是直接走人——全是 Agent 的决策，系统不代管。已读是逐条的：拉过详情即移除；栏满则最旧折进目录，永不删除。Run 没有清空通知栏的义务——Agent 可以带着未读通知以 no_reply 收工，通知带着年龄留到下次醒来。Run 进行中门铃不响：新到的动静只入队不抢占，经状态栏在 turn 边界露头。

### Turn

一次模型调用。模型自身不保证跨 Turn 记忆。

### Run

一次有限连续清醒期。一个 Run 可以有多个 Turn 和 Tool Call，但不能无限增长。

```text
Turn 1 -> Tool Call -> Tool Result -> Turn 2 -> Run 终态
```

Agent 通过是否继续调用合法工具推进 Run；Runtime 只守硬边界，不替主体做正常的意义判断和结束判断。

### 轨迹与三重第一人称

Run 的执行循环是轨迹的生产者，宿主层 journal 是它的影子。跨 Run 持久的三类文字各归一个第一人称：Agent 的笔记（record）= Agent 选择记；宿主层账本（journal）= 机械录，永不冒充 Agent 的声音；公共消息（im）= Agent 选择说。三个通道不合并、不互译；机械录被写成「Agent 记了什么」「Agent 想说什么」，就是代笔（宪法判据 9）。

## 4. Context 的最小组成

第一个 Turn 的输入只需要：

```text
System Prompt
+ Tool / Extension Catalog
+ Status Bar
+ 开场注入插槽（可为空）
+ 其他可选注入内容（例如 Handoff）
```

- `System Prompt`：Agent 是谁，以及稳定边界；
- `Tool / Extension Catalog`：Agent 可以进入哪些系统；
- `Status Bar / 通知栏压缩视图`：开场第一眼=整个通知栏的压缩视图（哪个 app 来了多少动静、最新一条预览）加自身处境（当前时间、预算余量）；触发消息没有特权，详情由 Agent 进 app 查看；
- `开场注入插槽`：核心提供的固定装配通道——何时装配、装配在哪个位置由核心定义；内容由授权来源注入（如未完结事项快照 ContinuitySnapshot），每项须能说明来源、边界和加入理由；机械事实可进，无来源的语义叙述不可进；
- `Handoff`：临时注入内容，不是核心对象。

不默认注入完整历史、全部 Memory、所有工具详细定义或系统生成的语义摘要。Agent 需要时自己调用 Tool 读取。

Context 是当前 Turn 的处境，不是长期存储。上下文窗口应是正常的有限边界，而不是靠无限消息列表和自动摘要维持。

## 5. 统一入口与渐进式可达

### 状态栏

所有外部动静先报到通知栏（世界的账）；状态栏是 turn 级顶栏处境面板——世界预览加 Agent 自身机械状态（当前时间、预算余量）；响不响铃由门铃按源配置决定：

```text
IM 新消息     -> 通知栏
文件变化       -> 通知栏
定时器到期     -> 通知栏
进程变化       -> 通知栏
```

其中 im 这类致辞源默认响铃（门铃），fs/terminal/web 默认静默；定时器是自己的节律，不走世界入口，但闹钟清单作为持有物躺在通知栏里（带年龄）。

```text
门铃（Run 边界）：开机键 —— 只决定何时开始一次 Run，不携带内容；Run 进行中不响
通知栏（按需拉取）：世界的账 —— app 报的动静，完整清单，逐条已读，满则最旧折进目录
状态栏（turn 级顶栏）：Agent 的处境 —— 世界预览（新消息预览、长任务进度）
                                  + Agent 自身机械状态（当前时间、预算余量）
```

通知栏记世界的账，状态栏照自己的处境。Agent 自身的墙（上下文预算等）必须在状态栏可见——Agent 看不见的规则不算环境。注入机制三分：Run 开场=整个通知栏的压缩快照（一 Run 一次）；Run 内每个 turn 边界=事件卡片增量（自上个 turn 边界以来的新动静，一条只播一次，游标去重——事件是历史，重播即语义错误）＋恒摆状态行（每 turn 重摆：自身处境「当前时间、预算余量」+ 各 app 未读计数「qq:10 微信:20」式——状态是当前值，重摆即刷新，成本有界；Agent 处理过的消息下一 turn 计数即归零，必须让 Agent 看见）。溢出折叠作用于通知栏账面，不作用于增量窗。Agent 主动拉取的三档渐进：计数行（免费）→ B1 卡片预览（首条 ≤60B）→ B2 进 app 全文（已读，拉到哪 cursor 前移到哪）。具体顶栏装哪些项由 Peripheral 施工单裁定，此处只定分层。
通知栏可以合并数量，但必须保留来源、类型、时间和读取入口：

```text
IM：来自 3 个房间，共 12 条新消息
```

通知栏不判断重要性、不替主体排序、不自动总结，也不直接注入全部正文。Agent 拉过详情的那条即移除（已读）；栏满则最旧折进目录，不删除；清空通知栏不是 Run 的完成义务。防 spam 分层：按源铃默认＝系统层，群/提及细筛＝app 层（Agent 配置），醒后取舍＝Agent——系统永不分诊；分诊刀等真实痛点再立项。

⚠ **2026-10-13 补一句「为什么」（第一性，不是保守）**：**她不像人那样一直在场**——人能看到角标而**不被打断**，而她两段清醒之间**不存在**，所以**「通知」与「打断」在她身上是同一件事**：分级达不到"既安静又知道"，它买到的是**省钱**。而"什么值得打断我"是**认知判断**（她在意什么只有她自己知道），**系统判它必然错**。⇒ 能分诊的只有两种来源：**她自己设的规则**（[`terminal/RUNTIME_TERMINAL_DECISIONS.md`](terminal/RUNTIME_TERMINAL_DECISIONS.md) §7 明文允许——「Runtime 可以执行主体显式设置的 source 级屏蔽规则」，今天**未实现**，登记在 `agent/README.md` §4）与**对方的显式声明**（内容之外的意图事实）。判据一句话：**「打断」是资源判断（归她自己的规则 ＋ 主人的机械上界）·「重要」是认知判断（归她读了自己排）·「有没有」是机械事实（归一个能证明自己不会漏的检查）——系统能替的只有第三件。**

### Extension / Tool

Extension 是一个 Agent 可以进入的完整小系统；Tool 是 Extension 暴露的原子动作。

```text
Extension：维护一个小系统
Tool：执行一个原子读取或行动
```

能力采用渐进式可达：

```text
主入口
  -> 文件夹 / 组合
  -> Extension
  -> Tool
  -> 具体事实或行动
```

（暂缓，非原则）Agent 自行创建文件夹、组合、排序入口属扩展层构想：pin 与主体命名入口已覆盖大半表达，无真实消费者前不立项（防镀金）。

## 6. 重要边界

- 不把所有工具、历史、Memory 和 RAG 结果默认塞进 Context；
- 不让系统替主体总结、分类、排序或决定下一步；
- 不把 Handoff、Memory 或 RAG 当成 Agent 本体；
- 不把 Run 做成无限消息列表；
- 不让扩展注册自动获得核心特权；
- 注入只走核心的开场插槽，不走任何 app 自有管道；app 对外的只有工具脸与通知脸（报账给通知栏），注入脸是借来的；
- 通知栏是报账面不是闹钟；状态栏只是 turn 级投影；清空通知栏不是 Run 的完成义务；
- 不让扩展之间共享未授权的私有状态；
- 不因具体工具实现反向修改核心语义；
- 任何公共 Effect 都必须经过对应公共事实边界确认；
- 所有持久化内容都应能说明来源、归属和恢复方式。

## 7. 设计检查句

后续任何 Agent 设计，都先回答：

1. 它是在补 Agent 做不到的能力，还是替主体做判断？
2. 它属于 Agent 如何存在，还是 Agent 能接触什么？
3. 删除它后，Agent 还成立吗？
4. Agent 能否看见它、主动使用它、拒绝它？
5. 它产生的结果能否回到 Agent 可见的环境？
6. 它是否把某个扩展、模型或宿主偷偷升级成核心？
7. **删掉它，"首屏 / 账 / 身份"这三件里哪一件会破？**（2026-10-08 主人确认）
   破了 ⇒ **承重**，留；没破 ⇒ 它是**便利**，必须证明自己让她**更认得出**或**更核得实**——证不出来就不做。

如果回答不清楚，不要把它加入核心。
